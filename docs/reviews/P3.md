### F1 — ID-less tables lose required context and still pass readiness

At `literature/parse.py:_add_table`, `item_id` is only the optional XML `id`.
`literature/retrieval.py:_context` groups table context only when that field is
truthy. An otherwise valid table without `id` therefore loses its caption and
qualifying footnote in the bundle.

Independent fixture: two-column TEAD1 table with a caption, header, and footnote
stating that values are indirect associations rather than binding measurements;
remove only `<table-wrap id='t1'>`'s id attribute. Actual result:

```text
bundle passage kinds: [table_row]
extraction_ready: true
incomplete_reasons: []
readiness_problems: 0
```

A separate table with an ID and headers but no label/caption is also marked ready
without noting missing caption context. The existing checker only asks whether
already-discovered caption/footnote IDs are included; it cannot detect a missing
table association or absent required context. The original tests all supply IDs.

Required repair:

1. Give every table a stable internal identity derived from the source asset and
   table-wrap locator when necessary; preserve original XML IDs separately or
   clearly distinguish the fallback. Never merge all ID-less tables together.
2. Use that identity consistently in parsing, bundle assembly, and verification.
   Include required caption/footnotes or mark incomplete when unavailable or
   outside bounds. Define missing-caption policy explicitly; a missing required
   caption must not become silently complete. A label alone is not a caption.
3. Test at least two ID-less tables with different footnotes, no caption, and a
   required footnote that does not fit. Require the verifier to reject a falsely
   ready bundle after its qualifying context is removed.
4. Version changed interpretation/identity rules and publish a new immutable
   chain; preserve both previously reviewed chains and reuse compatible caches.

## R1 — Name matches are incorrectly promoted to resolved human gene identity

`literature/passages.py:candidate_name_mentions` assigns `hgnc_id` and
`resolution=resolved_candidate_name` solely from a case-sensitive name match.
The candidate list is human, but the publication/experiment need not be.

In the actual mention table, joining exact-name and PubTator records by
publication, passage, and exact canonical offsets yields **120 conflicting
record pairs across 119 distinct spans**: the name record claims a human HGNC ID
while the aligned PubTator record is non-human/unmapped or ambiguous. Examples
in `publication:0d77635293eb69047481` (PMID 38945958): TEAD1 → HGNC:11714 versus
NCBI Gene 21676; YAP1 → HGNC:16262 versus NCBI Gene 22601. NCBI identifies these
external IDs as mouse [Tead1](https://www.ncbi.nlm.nih.gov/gene/21676) and
[Yap1](https://www.ncbi.nlm.nih.gov/gene/22601).

Required correction:

1. Separate retrieval association with a human candidate from the resolved
   identity of the biological entity in the passage. An exact name can carry
   `candidate_hgnc_id` (or an equivalent explicit hint), but must not establish
   human species or a resolved human mention by itself.
2. Keep source-specific identifiers and species evidence/unknown status. A
   species-compatible source identifier can resolve; unresolved/non-human or
   conflicting annotations remain explicitly so. Do not automatically map mouse
   orthologs onto human HGNC IDs or let a name match override another identifier.
   No new species classifier or external mapping service is needed: unknown is
   an acceptable conservative result.
3. Reconcile overlapping mention records or expose their conflict clearly. Keep
   exact hits usable for retrieval without presenting them to P4 as resolved
   entities. Bundle query/candidate IDs are retrieval context, not extracted genes.
4. Check external annotation text against its own offsets before rematching to
   canonical text. Do not attach an identifier to an arbitrary sliced string
   when the annotation and source location disagree.
5. Add real-artifact conflict validation and focused fixtures for a mouse mention,
   unknown species, consistent human identifier, and conflicting same-span IDs.

## R2 — Table structure and missing context are not preserved conservatively

`parse.py:_add_table` zips header rows without handling `rowspan`/`colspan`.
A two-level fixture with `Gene` spanning two rows and `Treatment` spanning
Control/IPF produces `Gene / Control | Treatment / IPF` for the three-value row
`TEAD1 | 1 | 3`. This falsely associates experimental columns. The real JATS
assets also contain span attributes (33 and 502 cells in the two table-bearing
articles), so span handling is relevant to the supplied corpus.

Separately, a table row with no header produces a bundle with
`context_complete=true` and no note. Flattened BioC tables cannot be assumed to
have recoverable column semantics. `_context()` also does not request table
footnotes for a table-row anchor.

Required correction:

- Preserve table cell structure, header spans, captions, and footnotes with their
  source locators. Either expand spans correctly or explicitly mark unsupported
  layouts; do not synthesize misleading header/column associations.
- For quantitative table-row bundles, include required header/caption/footnote
  context within the existing bounds. If absent, ambiguous, or too large, mark
  incomplete with a reason or exclude from extraction-ready bundles. Preserve
  source text for inspection; do not discard the paper or invent headers.
- Add fixtures for multirow/spanned headers, no header, flattened BioC, and a
  qualifying footnote that does not fit. Verification must reject false
  completeness and incorrect table structure, not only validate character slices.

## R3 — Search/fetch artifact identity omits response content

`workflows/literature.py:_request_outcomes` returns only `(cache_key, outcome)`.
The request cache key identifies URL/parameters, not returned bytes. Both search
and fetch stage identities use that list without response hashes. If a refreshed
response changes under the same request, the stage may return REUSED for the
old artifact after reading new data, instead of publishing new provenance.

The reviewer changed a synthetic successful RequestRecord's SHA-256 from hash-A
to hash-B: the identity component was identical.

Required correction:

- Include response/asset content hashes for successful source reads in stage
  identity. Preserve equal identity for the same bytes whether fetched or cached;
  exclude timestamps, request counts, credentials, and contact details.
- Preserve classified failure outcomes so recovery can create new lineage.
- Ensure passage identities distinguish changed canonical text/normalization
  versions, and bundle identities distinguish changed selected content. A stable
  raw asset plus XPath alone must not silently reuse an ID for revised canonical
  text. Preserve raw-source identifiers separately.
- Test same request/same bytes → reuse and same request/different valid bytes →
  new artifact, for search and fetch, with no overwriting of prior artifacts.
  Test changed canonical text identity as well. No live cache clearing needed.

## R4 — Enforce the embedding contract before encoding

The current selected-model run uses 1,000-character chunks and reports a
1,024-token model. However, `EmbeddingSection(max_chunk_chars=5000)` is accepted,
backend construction never checks that setting against the model, and query
text bypasses chunk bounds altogether. The manifest unconditionally states
truncation is impossible. The final verifier may notice an oversized setting,
but only after encoding and publication. Its embedding check also assumes
Ollama-specific `identity.metadata`, absent from the Sentence Transformers branch.

Required correction:

- Validate the actual selected model's input limit, special-token allowance,
  and query/document encoding requirements before requests. Reject unsupported
  settings or enforce a verified safe bound/explicit no-truncation mechanism.
  Apply this to queries too. A character/token bound specific to this BERT model
  must not be asserted for arbitrary selectable models.
- Record what was actually validated; do not unconditionally claim no truncation.
  Keep the current installed model and avoid another model download/tokenizer
  project. A clear unsupported-configuration error is acceptable.
- Make verification backend-aware using a common recorded encoding contract.
  Add offline tests for an oversized limit/query, a smaller model context, and
  Sentence Transformers verification metadata, without downloading weights.
